# Building and shipping agents

An installed agent is a binary in the cache (`%LOCALAPPDATA%\liberaqt\agents\<tag>` on Windows,
`$XDG_CACHE_HOME/liberaqt/agents/<tag>` elsewhere). `LIBERAQT_AGENT_PATH` names a directory of
`<tag>/` prefixes that shadows the cache. A checkout never updates either, so after any change
under `agent/`, rebuild every ABI you will verify against. Whether the right one then *loads* is
`agent-loading`'s subject.

## The quick path

```bash
liberaqt agents kits                 # Qt kits on this machine an agent can be built from
liberaqt agents build --tag <tag>    # configure, build, install, verify
liberaqt agents list                 # tag, revision, and where each came from
liberaqt doctor                      # every installed agent; one missing its own key is STALE
```

`agents build` derives the tag from the kit that was really configured, reconfigures every time so
the revision is current, and checks the installed binary for its plugin key before reporting
success. Its MinGW matching (`find_mingw()` in `agent_build.py`) is narrower than it sounds: a kit
whose name carries a version (`mingw81_64`) gets that MinGW, but Qt 6's plain `mingw_64` kit gets
the *newest* `Tools/mingw*_64`. That is right here only while GCC 11.2 is the newest installed;
install a newer MinGW and the Qt 6 agents silently link the wrong libstdc++. It writes the agent cache, so it is not
pre-approved in `.claude/settings.json`; ask before running it.

## By hand, per ABI

Use a separate build directory per ABI, because two configurations cannot share one. On Windows,
always pass `-G Ninja`: the "MinGW Makefiles" generator chokes on drive-letter colons. The install
layout must be `<prefix>/plugins/generic/liberaqt.{dll,so}`, since `QT_PLUGIN_PATH` is pointed at
`<prefix>/plugins`.

Linux:

```bash
cmake -S agent -B build/agent -DCMAKE_PREFIX_PATH=$QTDIR -DCMAKE_BUILD_TYPE=Release
cmake --build build/agent --parallel
cmake --install build/agent --prefix ~/.cache/liberaqt/agents/qt6.7-linux-x86_64-gcc
```

Windows, MinGW, Qt 6.7 (PowerShell). Use the MinGW the kit was built with; for 6.5 and 6.7 that
is GCC 11.2, and another GCC links a different libstdc++ than the application loads:

```powershell
$env:PATH = "C:\Qt\Tools\mingw1120_64\bin;C:\Qt\6.7.3\mingw_64\bin;$env:PATH"
cmake -S agent -B build/agent -G Ninja -DCMAKE_PREFIX_PATH=C:/Qt/6.7.3/mingw_64 `
      -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=C:/Qt/Tools/mingw1120_64/bin/g++.exe
cmake --build build/agent --parallel
cmake --install build/agent --prefix "$env:LOCALAPPDATA\liberaqt\agents\qt6.7-windows-x86_64-mingw"
```

Windows, MSVC 32-bit, Qt 5.15: what Libero SoC needs, and what was long believed impossible on
this machine. Visual Studio 2022 BuildTools **is** installed. Qt 5.15's 32-bit kit is
`C:/Qt/5.15.0/msvc2019`, because Qt names 32-bit kits without a suffix (`msvc2019_64` is the
64-bit one). MSVC toolsets v140 to v143 are binary compatible, so VS2022's compiler links fine
against a Qt built with 2019. Run this from `cmd` or a `.bat`, because `vcvarsall` sets the
environment only for the shell it runs in:

```bat
call "C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvarsall.bat" x86
cmake -S agent -B build/agent-msvc32 -G Ninja -DCMAKE_PREFIX_PATH=C:/Qt/5.15.0/msvc2019 -DCMAKE_BUILD_TYPE=Release
cmake --build build/agent-msvc32 --parallel
cmake --install build/agent-msvc32 --prefix "%LOCALAPPDATA%\liberaqt\agents\qt5.15-windows-x86-msvc2019"
```

Driving an application afterwards does not need Qt on `PATH`, because the application loads its
own DLLs from its own directory.

## The manifest

An installed agent carries `liberaqt-agent.json` at its prefix root, generated by the agent's
CMake: revision (`git describe`), Qt version, plugin key, compiler, bitness, protocol.
`agent_install` adds `source` and `archive_sha256` when the bits came from an archive. Without a
manifest an install is an anonymous `.dll`, and "is mine older than the fix I pushed?" has no
answer. That is why every agent built before stamping reports its revision as `unknown` rather
than pretending.

**The revision is resolved at configure time**, so a bare `cmake --build` after new commits keeps
the old value. `liberaqt agents build` reconfigures every time, which is the path that matters.

**Commit before building.** The revision comes from `git describe --dirty`, so a build from an
uncommitted fix is stamped `<sha>-dirty`, exactly like a build without it, and nobody can later tell
the two apart. The hello banner reports only the CMake version, which does not change.

**Rebuild every installed tag, not just the one you test against**, and close every application
that has an agent loaded first (Windows will not replace a loaded DLL). Two installed tags can share
a plugin key (`qt5.15-windows-x86_64-msvc2015` and `-msvc2019` both advertise
`liberaqt_5_15_64_msvc`), and the one that sorts first on `QT_PLUGIN_PATH` is the one a process
loads, so rebuilding only the other leaves the old code running.

## `liberaqt agents update`

```bash
liberaqt agents update --check        # what is behind; downloads nothing, exits 1 if anything is
liberaqt agents update                # refresh the ones that are
liberaqt agents update --tag qt6.5-windows-x86_64-mingw
```

`update` compares the installed `archive_sha256` with the **64-byte checksum** published beside
the archive, so checking every ABI costs almost nothing. `--check` exits 1 when something is
behind (the `ruff format --check` convention), so CI can gate on it. Every state is reported as
itself rather than collapsed into another:

| State | Meaning | Action |
|---|---|---|
| update available | a newer release exists | replaced |
| damaged | the binary on disk lacks its plugin key | replaced. The recorded checksum can only say "the release has not moved", never "these bits are intact", so the file itself is checked |
| local build | no published counterpart, usually *newer* than a release | left alone, even when damaged; `agents build` refreshes it |
| not managed | the build lives on `LIBERAQT_AGENT_PATH`, not in the cache | never written. Update used to read that copy and write to the cache it shadows, so it said "updated" on every run and never converged |
| could not check | unreachable, or the `.sha256` is not a checksum (an HTML error page served with a 200) | none. Kept distinct from a 404, which it used to be reported as |
| cannot tell | either no manifest, so it predates version stamping, **or** a 404 — the detail then reads "nothing published for this ABI at that location" (Qt 5.15 msvc2015 and the arm64 kits have no CI runner) | reinstall to get a manifest; nothing to do for a 404 |

Every state but "update available" and "damaged" exits 0, so `--check` passing does not prove a
local build has a fix: compare the revision `agents list` prints with the fix commit
(`git merge-base --is-ancestor <revision> <fix>`).

Update considers only `agent_registry.effective()`, one build per tag (the one a launch uses), and
never `installed()`, which lists a tag once per directory.

## `liberaqt agents install`

**It validates before it replaces.** It unpacks into a dotted staging directory beside the cache
(the registry skips dotted names), checks *those* bits rather than `installed()`'s first match for
the tag (which may be a copy on `LIBERAQT_AGENT_PATH`), stamps the manifest, and only then swaps
the new prefix in. It used to delete the live prefix first, so a refused reinstall destroyed a
working agent and left the refused one in its place, provenance and all, which `doctor` then
reported as a match.

A `--tag` that is not tag-shaped (`qt<minor>-<platform>-<arch>-<compiler>`) is refused. It
becomes a directory name, and `--tag ../../x` used to unpack outside the cache.

Archives live at `<base>/<tag>.zip`, with an optional `<tag>.zip.sha256`. The default base is
`https://github.com/sargis2000/LiberaQt/releases/latest/download`, a GitHub alias for the newest
release, so the URL never needs bumping. `LIBERAQT_AGENT_BASE_URL` overrides it (for an internal
share), and `--from` overrides everything for a one-off.

## Publishing: how a fix reaches everyone else

Tag a release. Pushing a `v*` tag runs the `publish` job in `.github/workflows/ci.yml`, which
attaches the archives to the release, and everyone else's `liberaqt agents update` picks them up.
Pushing a tag is outward-facing, so confirm with the user first.

The `agent` job builds eleven ABIs -- Linux gcc for 5.15, 6.5 and 6.7; Windows MSVC 5.15 x86
and x86_64, 6.5 and 6.7; Windows MinGW 5.15 x86 and x86_64, 6.5 and 6.7 -- and packages every
one as `<tag>.zip` plus `.sha256`. Each leg first runs `.github/scripts/agent_smoke.py`, which
launches the kit's own Qt Assistant with the fresh agent and fails unless it attaches under the
plugin key the tag implies and resolves selectors, so an agent that would not load is never
uploaded. Nothing else of `agent/src/` is exercised in CI; input and waits are `tests/e2e/` only.

Qt 6.5 and 6.7 MinGW were built with GCC 11.2 (their `mkspecs/qconfig.pri` says so), and an
agent built with another GCC links a different libstdc++ than the application loads. aqt offers
11.2 under a misleading name, `tools_mingw90` / `qt.tools.win64_mingw900` ("MinGW 11.2.0
64-bit": the 9 is mingw-w64's runtime version). That was once read as GCC 9, and those two
agents were shipped from local builds; CI now builds them with the right compiler.

The current release, `agents-77c72cc`, predates this: it was uploaded by hand from this
machine's nine local builds, so it has no Linux agents and no Qt 6.5 MSVC one. Because
`releases/latest` follows the newest release, the next `v*` release replaces it as what
`agents install` downloads, so that release must carry every tag users rely on. The two local
extras (`qt5.15-windows-x86_64-msvc2015`, `qt6.7-windows-x86_64-msvc2022`) are covered by the
msvc2019 builds of the same Qt, since MSVC 2015-2022 are one family.

The matrix's `arch` and tool names are checked against `aqt list-qt` and `aqt list-tool`. The
first version guessed them and failed every Qt 6 leg. Check the same way before adding a leg.
